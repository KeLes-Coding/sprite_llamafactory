# v3.3.0 LoRA（gemma3-270m）评测报告：验证集 vs Challenge-50

日期：2026-10-05　模型：`gemma3-270m-lora-v330`（`saves/gemma3-270m/lora/sft_v330_merged`，vLLM 0.11.0 DP8）

## 1. 结论摘要

| 评测集 | 性质 | 基准兼容准确率 |
|---|---|---|
| validation_2k | 与训练同一生成器；88% 的语义 ID 与训练集重合 | **98.75%** |
| challenge_50 | 训练后独立撰写，与 v3.3.0 训练/验证集零精确重合 | **32%（16/50）** |

- 与历史基线对比（同一 challenge_50）：旧全量 SFT 20%（10/50），qwen-flash 生产提示词 90%（45/50）。
- v330 相对旧 SFT：新增通过 12 题，丢失 6 题。McNemar 检验不显著（p≈0.24）。**整体提升不能确认**，只有 unseen_value（0→5）的改善比较明确，很可能来自工具 schema 新增的枚举含义描述。
- 98.75% 与 32% 的差距说明：模型学会的是「生成器的句式和拼接方式」，而不是「理解指令再规划」。

## 2. 这算不算过拟合？

**不是经典意义的过拟合，而是训练分布太窄导致的捷径学习。验证集的设计让这个问题无法被发现。**

- 经典过拟合是指训练太久、记住了训练集里的噪声，表现为验证 loss 回升。本次 eval_loss 一路下降到 0.0034，验证准确率 98.75%，没有这种迹象。
- 但验证集与训练集共享 88%（16,395/18,610）的 semantic_id，它测的是「同一语义换个表面形式」，本质上仍是训练分布。所以它只能说明「把训练分布学会了」，测不出分布外泛化。
- challenge 的失败高度集中在训练数据完全没有覆盖的语言现象上（见第 4 节），这属于覆盖缺口，不是训练步数问题。调学习率、提前停止、加正则都解决不了。
- 从结果上说，「验证集上近乎满分、换一种说法就不行」正是工程上通常所说的过拟合症状。准确的说法是：**对生成器分布过拟合（distribution overfitting）**，根因在数据，不在训练配置。

## 3. 训练数据诊断（v3.3.0）

| 指标 | 数值 | 含义 |
|---|---|---|
| 训练行数 | 171,900 | — |
| 不同 instruction 数 | 34,380 | 每条 instruction 出现 5 次（1 次真实工具名 + 4 次别名），真正的语义多样性只有 1/5 |
| 不同 semantic_id | 19,300 | — |
| 正例 / 反例 | 83,095 / 88,805 | **反例并不少，占 52%** |
| 每条样本的任务数 | 1 个：5.6%；2–3 个：20.9%；4–6 个：31.5%；7 个及以上：42.1% | 长串拼接占主导，单意图样本极少 |

**反例只有一种形态。** 反例几乎全部来自 `l0_neg_*` 原子，形式是「能力询问 / 闲聊 → reply」，例如「Can you clap? → State whether you can clap」。这些反例绝大多数被拼接进 7–10 个子意图组成的长串中，用「另外 / 还有 / 对了」连接。

训练集（真实工具名的 34,380 条）里覆盖不到以下句式：

| 现象 | 训练集覆盖 | challenge 中的例子 |
|---|---|---|
| 否定约束「不要 X，只做 Y」 / "don't / without" | 抽查命中的基本都是「特别」「道别」这类误命中，或 "without" 作普通介词，没看到真正的约束用法 | 031 / 034 / 038 / 039 / 040 |
| 收尾话术「再说一句…」"finish with 'X'" | 0 | 011 / 015 / 018 / 031 / 049 |
| 提及而非执行（复述、解释、假设） | 0 | 041 / 047 / 048 |
| 纠正「不是 X，是 Y」 | 0 | 050 |
| 带数字或坐标等干扰信息 | 0 | 010 / 012 / 017 / 025 / 036 |
| 消歧说明（「我说的查资料是指内部知识库」） | 很少 | 044 / 045 / 046 |

所以回答「这版没有反例吗」：**有，而且超过一半，但只覆盖了「能力问句 → 回复」这一种反例。** challenge 里的反例是另外几种（约束、提及、纠正、解释），模型完全没见过。旧版反例表现一直差，也是同一个原因。

## 4. Challenge 失败归因（34 题，按主因划分）

| 主因 | 题数 | 典型表现 |
|---|---|---|
| A. 过度拆分 / 编造额外任务 | 11 | 「跟我击个掌，然后说声配合愉快」→ 第二句被做成 `clap` 手势；「翻翻内部资料」→ `walk` |
| B. 否定 / 提及 / 纠正被当成执行 | 8 | 「不要移动…只查电量」→ 先执行了 `walk`；「解释 Gee 是什么，不要跳」→ 直接跳了 |
| C. 坐标噪声 | 5 | 坐标文本被拆成额外的 `web_search` 或 `get_weather` 任务 |
| D. 工具路由错误 | 5 | 「不要查内部库，去公网搜」→ 用了 `rag_query`；「查内部资料里的自由度」→ 用了 `get_weather` |
| E. 枚举 / 参数错误 | 4 | 编造舞蹈名 `ant-ap-dance`；「原地舞」映射成了 `warm_up_dance` |
| 其他（8 任务长序列） | 1 | 028 |

A 和 B 合计占 56%。它们在机制上是一回事：训练数据教会了模型「每个分句对应一个任务」，因为 42% 的样本都是 7 个以上分句的拼接。模型从没见过「分句是修饰、约束或话术，不产生任务」的情况。

**口径说明：** C 类 5 题的提问是按 v3.2.0 带坐标的天气 schema 写的，对 v3.3.0 并不公平。去掉这 5 题后准确率为 16/45 = 35.6%，结论不变。challenge 只有 50 题，95% 置信区间大约在 21%–46%，只适合看大的趋势。

## 5. 「很难枚举」怎么办

表面说法确实无法枚举，但**决定规划结果的语言现象是有限的**，可以枚举。方法是把数据生产拆成几个相互独立的维度，在维度上做组合覆盖，而不是去穷举句子。

```
样本 = 意图内容 × 语言算子 × 干扰信息 × 结构长度 × 表述风格
```

| 维度 | 是否可枚举 | 取值示例 |
|---|---|---|
| 意图内容 | 可以（工具 × 枚举值，已有原子库） | 7 个工具、25 种舞蹈、13 种手势、6 种状态… |
| **语言算子**（新增重点） | 可以，约 12–15 种 | 直接执行、能力询问、否定约束、只做 / 仅、纠正、提及 / 复述、解释 / 假设、条件、收尾话术、消歧声明、指代（「它」「刚才那个」）、次数限定 |
| 干扰信息 | 半枚举（按类型） | 数字、坐标、人名或地名、引号内容、无关的背景叙述 |
| 结构长度 | 可以 | 1 / 2–3 / 4–6 / 7+ 个任务，需要重新配比 |
| 表述风格 | 不枚举，交给 LLM 改写 | 口语、书面、啰嗦、省略、中英混杂、错别字 |

要点：

1. **语言算子是关键维度。** 每个算子决定的是「这一段文字是否产生任务、产生什么任务」，规则是确定的，可以写成生成规则加自动标注。例如否定约束对应「被否定的部分不产生任务，剩下的部分正常规划」。
2. **用最小对比对（minimal pairs）来造反例。** 同一段内容只改一个算子，标签就随之变化：
   - 「跳一段 Gee」→ action
   - 「你会跳 Gee 吗」→ reply
   - 「不要跳 Gee，说一下它是什么」→ reply
   - 「说明书写着‘跳 Gee’，复述一下」→ reply

   这样模型被迫去看算子，不能只认关键词。反例因此不需要枚举，只需要「每个正例都配上 2–3 个算子变体」。
3. **只有表述风格交给 LLM 改写，标签由规则决定。** 改写后用契约校验加回译一致性过滤，保证标签不会漂移。
4. **用 Teacher 蒸馏补长尾。** qwen-flash 在 challenge 上达到 90%，可以让它给大量 LLM 生成或线上真实的说法打标签。只保留同时满足以下条件的样本：契约合法、与规则生成的标签不冲突（或两个 teacher 结论一致）。这条路覆盖的是「想不到的说法」，与枚举互补。
5. **调整长度配比。** 把 1–3 个任务的样本从 26.5% 提到大约 60%，长串拼接降到 20% 以下。challenge 和真实对话大多是短句，长串拼接正是「每个分句对应一个任务」这个习惯的来源。

## 6. 下一步计划（按优先级）

| 优先级 | 事项 | 产出 / 验收 |
|---|---|---|
| P0 | **建立分布外测试集体系**：challenge_50 封存为测试集，生成器作者只看类别说明，不看题目；再扩写 challenge v2（每类 ≥30 题，覆盖第 5 节的算子维度，按 v3.3.0 无坐标 schema 撰写） | 每次训练后在 validation 和 challenge 上并列报告，以 challenge 为主指标 |
| P0 | 数据生成器加入「语言算子」维度和最小对比对反例，算子规则写成可测试的自动标注 | 每种算子都有单元样例；数据统计报告列出算子 × 工具的覆盖矩阵 |
| P1 | 重新配比任务长度，并降低别名样本的重复倍数（4 倍别名会稀释语义多样性） | 1–3 个任务的样本约占 60% |
| P1 | 统一已知的标签冲突：「can you + 动作」何时执行、何时回复；英文舞蹈名的翻译映射（来自 val2k 的 26 个错误分析） | 冲突规则写入生成器文档和校验 |
| P1 | 用 Teacher（qwen-flash）蒸馏补长尾说法，规则加契约双重过滤 | 蒸馏样本占比和过滤率可追踪 |
| P2 | **区分是容量问题还是数据问题**：用同一份 v3.3.0 数据训练 gemma3-1b LoRA 跑 challenge。如果 1B 也只有三四成，说明主要是数据问题；如果大幅提升，说明 270M 容量是瓶颈 | 一组对照实验 |
| P2 | 可选：在推理侧加一个轻量的规则后处理，例如被否定的工具直接剔除，作为过渡兜底（不替代数据修复） | 需要单独评估，避免掩盖模型问题 |

## 7. 本次评测的意义

1. **首次量化了「分布内 vs 分布外」的差距**：98.75% 对 32%。它证明现有验证集不能用来做上线判断。
2. **定位了根因在数据覆盖，而非训练配置**：LoRA 配置、模板对齐、模型合并部署都已验证无误；继续调超参的收益很低。
3. **澄清了反例问题**：反例数量足够（52%），问题在于只有一种形态。
4. **评测工具链已支持 v3.3.0+**：支持 jsonl、别名反解、`--vllm-only`，challenge 会自动取真实工具名作为参考行并做天气 schema 投影，后续每版数据都能直接复跑。
