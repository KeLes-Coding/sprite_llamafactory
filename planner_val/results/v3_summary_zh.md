**口径约定（均由用户拍板，按日期汇总）**

- 不称呼机器人。
- “能不能 / 可以…吗 / Can you X?”是能力问句，标为 reply；“Could you check…”这类请求调用工具。
- 推迟、条件句、愿望、假设，标为 reply。
- 唱歌、讲笑话、“说声 X”，标为 reply。
- 列表外的舞蹈或手势、舞名错字，标为 reply；不能凑一个相近的动作。
- 单纯的“拜拜 / 再见”标为 wave_greet_bye。
- 二选一时执行第一个。
- “边 X 边 Y”拆成两个任务，按原话顺序。
- 次数：手势、舞蹈拆成 N 个任务；移动用 step=N。
- 速度修饰忽略。
- “转一下”= 90°；“一点 / 稍微”= 15°。
- 查询类：
  - 有具体对象才调用工具，比如“能帮我查下北京天气吗”调用；“你会查天气吗”只回复。
  - 自身规格走 rag_query，实时状态走 robot_status，稳定常识直接回答，时效信息走 web_search。

### 1.2 阶段 2：英文原子（6,330 条被使用）

- 上游池的 `instructions.en` 质量不可用，比如舞名是拼音、“摇头”被译成 nod。英文由 `translate_atoms.py` 从中文原子重新翻译，舞蹈和手势名查固定的 `DANCE_EN` / `GESTURE_EN` 词表。
- 翻译跑了 3 个 run（en_atoms、en_full、en_full2），共 6,583 条，去重后剩 6,330 条进入拼装。
- **英文没有关系算子**（`relations=[]`）。

### 1.3 阶段 3：拼装（`assemble.py`）

| 配置 | 值 |
|---|---|
| 层级 | L1–L10（L = 任务数） |
| L1 | 每个原子恰好一条，约占 22%（`--l1-share 0.22`） |
| L2+ | 均分其余样本；qwen-max（T=0.7）把多个原子合并改写成一句话 |
| 判官 | qwen-max 对每个原子摘出原句中的引文（quote），代码校验引文存在且有序；写手重排了顺序的按引文位置重排，漏句的拒收 |
| 反例混入 | 每个槽位 neg_rate = 0.2 |
| 关系算子混入 | rel_rate = 0.15，仅中文 |
| 并发 / 种子 | 32；中文 seed=7，英文 seed=8 |

| run | 产出行数 | 拒收 | 良率 |
|---|---|---|---|
| `v340_zh-1007_180008` | 43,680 | 7,003 | 86% |
| `v340_en-1007_180524` | 33,022 | 3,900 | 89% |

L2 以上随层级升高拒收率上升：中文 L10 产出 3,523/4,862，英文 L10 产出 2,600/3,371。主要拒收原因是判官认为有句子被漏掉，或引文找不到。

### 1.4 阶段 4：导出（`runs/export_v340/v3-4-0-74a63ca3`）

- 两个语言的 run 合并后，用 seed=340 随机抽 1,000 条作为 `validation_1k`，其余 75,702 条为训练集。
- `augmentation: none`：**v3.4.0 没有做工具名或参数名掩码，也没有“缺工具”反例**。`augment.py` 已实现但未启用。
- 工具展示顺序在全部样本中只有 1 种（固定顺序）。
- 格式为 sharegpt messages：system 提示词 + user JSON（`tools` + `instruction`）+ assistant JSON 任务数组。单条 prompt 约 2,075 tokens。

## 4. 评测设置

### 4.1 推理

| 被测对象 | 推理方式 | 提示词 |
|---|---|---|
| 270M / 0.6B v340 LoRA | 远端服务器 vLLM（OpenAI 兼容接口，经 SSH 隧道转发到 8001 端口）；temperature=0，max_tokens=1024，并发 16 | 与训练相同的 system 提示词和 tools，取 v3.4.0 验证集第一行作为参考行 |
| qwen-flash（v340 提示词） | DashScope API | 与 SFT 模型完全相同 |
| qwen-flash（线上提示词） | DashScope API；`request_builders` + `benchmark_20260913` profile（subagent 3911119） | 线上提示词。其 get_weather schema 带 latitude/longitude，与 v3.4.0 契约冲突 |
| **qwen-flash（线上提示词，schema 校正）** | 不重新推理，对上一行的输出做机械映射后重新评分 | 只做两项等价映射：删去 get_weather 的经纬度；手势 / 舞蹈 `repeat=N` 展开成 N 个任务。**作为本报告的锚点**（下文简称 qf-锚点）；其余口径差异仍算 qwen-flash 的错 |

### 4.2 评分（`planner_val/scoring.py`）

**主指标 `benchmark_compatible_pass`**

1. 输出能通过解析，并满足契约：JSON 合法、工具和枚举存在、参数满足 schema。
2. 工具调用序列与期望一致，顺序也一致。
3. 期望中的 reply 槽位可以合并或跳过，不强求一一对应。
4. 参数比较规则：
   - get_weather、web_search、rag_query 不比参数。
   - HumanAction 的 step 和 degree 不比，x、y、yaw 只比符号。
   - repeat 不比。
5. 任何多出来的工具调用都算违规（`forbidden_tool`）。

**辅助指标**

- `strict_pass`：task 数量、kind、name 逐位一致，reply 槽也必须对齐。
- `parser_valid`：输出是否通过解析。
- 禁用工具违规率。
- 失败原因分 4 类：parser_rejected、forbidden_tool、tool_sequence_mismatch、parameter_mismatch。
- **参数严格分**（`/tmp/v340_generalization.py`）：在主指标通过的基础上，再要求 step、degree 精确相等，get_weather 的 city 互为子串、query_type 相等。主指标不查这些值，会把“转 200° 输出 180°”“雷克雅未克输出深圳”算作通过。

### 5.1 各评测集离训练分布有多远

从三个层面衡量：

- **字面**：把题目拆成子句，每个子句在原子子句库（中英文共 14,801 个原子）里找字符二元组 Jaccard 最近邻，取最生的子句作为整题得分。分数越低越陌生。
- **规划结构**：把期望答案归一成签名。签名包含工具名、动作 / 手势 / 舞蹈取值、移动方向符号、状态查询项和天气类型，忽略具体数字，相邻 reply 合并。然后看这个签名在训练集的 75,702 个答案里是否原样出现过。
- **参数值**：题目里的 step、degree、city 是否在训练集中出现过。

- degree 只有 11 个取值：15、30、45、60、90、120、135、150、180、270、360。
- step 只有 22 个取值，缺 12、13、17、19、23、25 等。
- city 只有 110 个。深圳出现 15,637 次，占全部 get_weather 任务的 49%，因为未提城市时默认深圳。

**判断**

- 字面上，三个 challenge 都远离训练句子：子句最近邻中位数只有 0.18–0.25，而 validation_1k 是 0.67。所以模型不是在背句子。
- 结构上，82–85% 的题目，其答案结构在训练集中原样出现过。challenge_v3 的参数值也几乎全在训练范围内（只有 1 题例外）。加上 v3 的判定规则本来就是按训练口径写的，它实际考的是“见过的答案结构 + 见过的参数值 + 见过的规则，只是换了说法”。
- 因此，challenge_v2 / v3 基本都在训练分布的覆盖范围内，不足以回答“换参数、换结构还能不能过”。这个问题由 probe_v1 回答，见 6.8。

### 6.7 qwen-flash 的对比需要打折

challenge_v2 和 v3 都是按咱们的约定口径标注的，qwen-flash 是零样本，不知道这些约定。线上提示词在 challenge_v3 上的 32 道失败，按成因拆分：

| 成因 | 题数 | 内容 |
|---|---|---|
| schema 格式不符 | ~10 | get_weather 带经纬度 8 题；`cancel_task`、`robot_status(query=time)` 等非法枚举 |
| 不知道约定口径 | ~11 | 列表外舞蹈、手势、唱歌、错字应回复（4 题）；次数要拆成多个任务（3 题）；续航→rag、海外时间→web、常识→直接回答（3 题）；能力问句（1 题） |
| 真正的理解错误 | ~11 | 顺 / 逆时针方向；改口不撤回（3 题）；对别人说当成对它说；倒装顺序；把“伦敦今晚下雨吗”路由到 web_search |

- 去掉经纬度并展开 repeat 后（即 qf-锚点）：challenge_v3 82/105（78%），challenge_v2 195/241（81%）。
- 换成 v340 提示词后，主要问题变成太保守：明确请求也只回复，比如“几点了”“电量怎么样”“Luna 保修政策”。另有 6 题在 JSON 后附加解释文字，导致解析失败。
- qwen-flash 确实更强的地方：显式路由（5/6 对 3/6）、“对个掌”、“拜财神舞”、“可别躺下”，以及用 v340 提示词时的倒装顺序。

**结论**：“0.6B 在咱们的口径上胜过 qwen-flash”成立，但这不代表通用语言理解更强。真正的语义错误数量，两者在同一量级。probe_v1 和 challenge_50 的结果（见 6.1、6.8）支持这一点：离开自家口径后，0.6B 与锚点持平或略低。

| 换问法 | 能过（9/9） | 持平 |
| 换话术 | 基本能过（17/19） | 持平。270M 只有 11/19，换话术就明显不行 |
| 换参数 | 不稳（32/41） | 落后。角度会吸附到训练见过的值，未见城市会被静默换成深圳。输出格式合法、主指标也算对，但实际参数是错的，是最危险的一类错误 |
| 换结构 | 不稳（16/21） | 略落后。“各”“都”“再来一遍”“除了”和编号列表都不在训练分布里 |

个别失败的例子见上表。probe_v1 只有 107 题，置信区间约 ±7 个百分点；而且和 challenge_v3 一样，是熟悉口径的助手写的。以上结论只是方向性的。

### 6.9 跨评测集的观察

1. **排序一致**：三个 challenge 上都是 0.6B > 270M。差距在 challenge_v2 上显著，在 challenge_v3 上不显著（10 对 6，p=0.45）。两者的失败形态不同：270M 偏漏项和编造，0.6B 偏把非请求执行掉。
2. **从“换说法”到“新形式”约掉 5–10 个百分点**：challenge_v2 是同一原子池换说法，0.6B 拿到 96.3%；challenge_v3 引入了池中没有的语言形式（顺时针、对掌、倒装、显式路由、长句撤回），0.6B 降到 85.7%。
3. **掉分集中在训练池缺失的形式**：challenge_v3 两个模型共同失败的 9 题，有 6 题可以在池中直接找到覆盖缺口（见 6.6 最后一列）。口语改写、ASR 噪声和中英混说，两个模型都满分或接近满分。
4. **v2 → v3 在 challenge_50 上显著提升**（0.6B 54% → 78%，270M 32% → 60%）。由于超参不变，这个提升可以归因于数据：反例种类、关系算子、口径统一。
5. **禁用工具（多余调用）仍是首要失败类型**：challenge_v3 上 0.6B 的 15 道失败中有 8 道是这一类，challenge_50 上 11 道中有 8 道。多余的物理动作在实际部署中风险最高。
6. **分布内已经饱和**：eval_loss 只有 0.004，validation_1k 已无区分度。后续要以 challenge 集为准。
7. **高分主要来自训练分布的覆盖**：challenge_v2 / v3 在字面上很陌生，但 82–85% 的答案结构在训练集中原样出现过，判定规则也和训练一致（见 5.1）。一旦离开这个覆盖范围，0.6B 的优势就消失：probe_v1 和 challenge_50 上，它与 qf-锚点持平或略低。
8. **主指标高估了 SFT 模型**：角度吸附、未见城市被换成深圳这类错误会被算作通过。正式对比应同时报告参数严格分。

## 7. 结论

1. **v3.4.0 数据有效。** 超参不变，两个模型在 challenge_50 上都显著提升（+24 / +28 个百分点）。parser_valid 接近 1，格式问题基本解决。
2. **还没有超过锚点。** 以 qwen-flash（线上提示词，只做 schema 校正）为锚点，0.6B 的表现如下：

   | 集合 | 0.6B 与锚点相比 | 显著性 |
   |---|---|---|
   | challenge_v2（同池改写） | +15 个百分点 | 显著 |
   | challenge_v3（按训练口径手写） | +10 个百分点 | 不显著 |
   | probe_v1（扰动） | −4 个百分点 | 不显著 |
   | challenge_50（独立旧题） | −8 个百分点 | 不显著 |

   领先部分来自训练分布和自家口径，而不是更强的理解能力。延迟上 0.6B 快约 5 倍。
3. **以 0.6B 为主。** 在 challenge_v2 上显著优于 270M。270M 换话术就明显不行（probe_v1 style 只有 11/19），在 challenge_50 上显著不如锚点。
4. **换说法和问法基本能过；换参数和结构不稳。** 具体问题：
   - 角度会吸附到训练中的 11 个取值。
   - 未见城市会被换成深圳，因为深圳占训练中天气任务的 49%。
   - “各 / 都 / 再来一遍 / 除了”和编号列表处理不了。
   - 显式路由、顺 / 逆时针、近义别称、倒装是共同盲点。
5. **0.6B 有过度执行倾向。** 条件句、列表外手势、点名他人的话会被执行，或被替换成近似动作。从安全角度看，这比漏执行更值得关注。
